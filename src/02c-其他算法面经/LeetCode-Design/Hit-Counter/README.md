# LeetCode Design — Hit Counter（命中计数器）

> 来源：LeetCode 362 *Design Hit Counter*（含其原题自带的高频 follow-up）。
> 这是 `LeetCode-Design/` 系列的第一题，沿用 Coinbase 练习的 scaffold 约定
> （单文件 `HitCounter.java`，每 Part 一个 `HitCounterPartN` 内部类，stub 抛
> `UnsupportedOperationException`，裸 `javac && java` 跑 `HitCounterTest`）。

设计一个命中计数器，统计「过去 5 分钟（300 秒）」内收到的命中次数。每次调用都带
一个**秒级** `timestamp`（调用方给，不读真实时钟）。

---

## API 全貌

```java
hit(int timestamp)            -> void   // Part 1：记一次命中
getHits(int timestamp)        -> int    // Part 1：过去 300 秒的命中数
// Part 2：API 不变，换成 O(窗口) 内存的实现
// Part 3+：见下方「扩展路线图」
```

**窗口语义（最容易错的点）**：`getHits(t)` 统计的是半开区间 **`(t-300, t]`**
内的 hit —— **含右端 `t`，不含左端 `t-300`**。所以 `t'=t-300` 的命中**不算**，
`t'=t` 的命中**要算**。

```
hit(1); hit(2); hit(3);
getHits(4)   == 3      // 1,2,3 都在 (-296, 4]
hit(300);
getHits(300) == 4      // 1,2,3,300 都在 (0, 300]
getHits(301) == 3      // t'=1 掉出 (1, 301]；留下 2,3,300
```

## 澄清问题（面试里值得先问的）

- **时间戳单调吗？** Part 1/2 假设单调非减（调用按时间顺序来）。**乱序/迟到**
  是后面专门的一个扩展（Part 4），到那时再放开。
- **同一秒能有多次 hit 吗？** 能。Part 2 的整个意义就是应对「同一秒海量 hit」。
- **窗口固定 300 秒吗？** Part 1/2 固定 300；「可配置窗口 + 任意区间查询」是扩展
  Part 3。
- **多线程并发调用吗？** Part 1/2 单线程；并发是扩展 Part 5。
- **要精确还是可近似？** Part 1–5 要精确；近似（省内存/分布式）从 Part 6 起讨论。

| 1 | 基础 hit / getHits | 窗口是半开区间 `(t-300, t]`，别把左右端点搞反 |

### Part 3 — 可配置窗口 + 任意区间查询

**真实场景**：监控大盘要画任意时间段曲线，不只是「最近 5 分钟」。

**问题陈述**：构造时给窗口 `W`；`getHits(t)` 统计 `(t-W, t]`；新增 `getHits(start, end)`
统计任意闭区间 `[start, end]`（含两端）。

**面试官最常追问**：
1. **「任意区间查询下，老数据还能丢吗？」** → 引出「固定窗口可以丢老数据、任意区间
   只能丢到某个保留期 retention」的矛盾。
2. **「`getHits(start,end)` 你打算 O(?)」** → 朴素遍历 O(区间) vs 前缀和 O(1) vs
   树状数组/线段树 O(log n)；以及「还在写入」时前缀和怎么维护。
3. **「区间跨度很大（几天）但粒度还是秒怎么办？」** → 给 Part 6 分层桶埋伏笔。
4. **「两个 `getHits` 重载语义怎么自洽？」** → `(t-W,t]` 在整数秒上 == `[t-W+1, t]`，
   让单参直接调双参。

**取舍表**：

| 结构 | hit | getHits(s,e) | 内存 | 备注 |
|------|-----|--------------|------|------|
| 逐秒桶 + 遍历 | O(1) | O(e−s) | O(保留秒数) | 区间大就慢 |
| 前缀和数组 | 追加 O(1) / 改历史难 | O(1) | O(保留秒数) | 写历史要重算后缀 |
| 树状数组 Fenwick | O(log n) | O(log n) | O(保留秒数) | 点更新 + 区间和 |
| TreeMap<秒,计数> | O(log n) | O(log n + k) | O(非空秒数) | 稀疏友好 |

**自检题**：
- `getHits(t)` 和 `getHits(t-W+1, t)` 必须相等吗？你的实现保证了吗？
- 查一个比所有数据都老的区间，返回什么？会越界吗？
- 前缀和方案下，一条迟到的历史 hit 进来要改多少个数？

### Part 4 — 乱序 / 迟到时间戳

**真实场景**：命中从多台机器汇聚，网络抖动让事件迟到、乱序，甚至补录历史。

**问题陈述**：`hit(t)` 不再单调；`getHits(asOf)` 仍统计 `(asOf-W, asOf]`，但迟到数据
会改变历史窗口的答案（同一个 `asOf` 先后问可能不同）。

**面试官最常追问**：
1. **「你 Part 2 的环形数组为什么这里就废了？」** → 环形数组靠「当前最大时间」定位
   slot，倒退/乱序就错位。要换按绝对时间索引的结构。
2. **「迟到能迟多久？有 watermark 上界吗？」** → 「允许的最大乱序」决定老数据何时能
   安全回收；超过 watermark 的迟到丢弃还是进特殊桶。
3. **「老数据怎么回收？」** → 按时间排序的结构（TreeMap / 最小堆）+ 惰性或定时清理
   `< seenMax − W − allowedLateness` 的桶。
4. **「乱序下还能用前缀和吗？」** → 能，但插入历史点要更新后缀 → 树状数组更合适。

**取舍表**：

| 结构 | 乱序插入 | 区间查询 | 回收老数据 |
|------|----------|----------|-----------|
| TreeMap<秒,计数> | O(log n) | subMap O(log n + k) | tailMap 砍老 key |
| 树状数组(时间域有界) | O(log n) | O(log n) | 需滚动/有界时间域 |
| 最小堆按时间 | O(log n) | 差 | 弹最早 |

**自检题**：
- 同一个 `asOf` 先后问两次，答案可以不同吗？为什么？
- 比 watermark 还老的迟到数据来了，怎么处理才不破坏已回收的状态？
- 时间域可能为负或非常大时，固定数组还行吗？

### Part 5 — 并发（Coinbase 最爱追问）

**真实场景**：高 QPS 服务，几十个线程同时打点，监控线程并发读。

**问题陈述**：N 线程并发 `hit`，一些线程并发 `getHits`。要求无丢更新、读到一致
状态、读写不互相长时间阻塞。

**面试官最常追问**：
1. **「热点 bucket（同秒所有线程都在加）怎么减少竞争？」** → `AtomicLong` CAS 自旋
   vs `LongAdder`（分散到多 cell，读时求和）。
2. **「`getHits` 要不要加锁？读到加一半的桶可信吗？」** → 原子读单桶 OK，但跨桶求和
   不是原子快照——是否需要强一致，弱一致可不可接受。
3. **「一把大锁有什么问题？」** → 读写全互斥，高频 hit 把 getHits 饿死；引出
   ReadWriteLock / 分段锁。
4. **「滑动清理过期桶和并发 hit 怎么不打架？」** → 重置某 slot 时要与正写该 slot 的
   线程协调（CAS 重置 or 锁该桶）。

**取舍表**：

| 方案 | 写并发 | 读一致性 | 复杂度 |
|------|--------|----------|--------|
| synchronized 大锁 | 串行 | 强 | 低 |
| ReadWriteLock | 写串行/读并发 | 强 | 中 |
| 每桶 AtomicLong | 高 | 弱(逐桶) | 中 |
| 每桶 LongAdder | 最高(抗热点) | 弱 | 中 |

**自检题**：
- hit 在「自增」与「判断/重置过期桶」之间有竞态吗？
- getHits 求和期间别的线程改了桶，返回值算哪个时刻的？面试官接受吗？
- `LongAdder.sum()` 不是原子快照，对这题要紧吗？

### Part 6 — 超长窗口 / 省内存

**真实场景**：要「过去一天 / 一周」的命中。秒级桶一天 86400 个、一周 604800 个，再
乘 key 数，内存吃不消。

**问题陈述**：用可配置粒度 `bucketSeconds` 把命中聚成粗桶，精度换内存；窗口边缘落在
桶中间时近似。

**面试官最常追问**：
1. **「粒度多粗才够？误差多大？」** → 窗口边缘最多差一个桶（绝对误差 ≤ 一个桶内命中数）。
2. **「能不能边缘精确、中间粗？」** → 分层 rollup：近端用秒桶（精确），更老的滚成分钟、
   小时桶（粗），读时分层求和。
3. **「只关心趋势不关心精确值呢？」** → 指数时间衰减计数器（EWMA / 衰减计数），O(1)
   内存近似「最近活跃度」。
4. **「一天的桶怎么和 Part 5 并发结合？」** → 桶一多，锁/原子粒度怎么定。

**取舍表**：

| 方案 | 内存 | 精度 | 适合 |
|------|------|------|------|
| 秒桶 | O(窗口秒数) | 精确 | 短窗口 |
| 定粒度粗桶 | O(窗口/粒度) | 边缘近似 | 中长窗口 |
| 分层 rollup | ~O(log 跨度) | 近端精确远端粗 | 超长窗口 |
| 指数衰减 | O(1) | 趋势近似 | 只要趋势 |

**自检题**：
- getHits 在窗口左边缘那个半截桶怎么算？高估还是低估？
- 分层 rollup 里一个 hit 要更新几层？读要读几层？
- 衰减计数器还能精确回答「过去 X 秒命中数」吗？

### Part 7 — 分布式 / 分片

**真实场景**：单机扛不住命中量 / 内存，按 key 分散到 N 分片；查询时合并。统计独立
用户数时引出近似去重。

**问题陈述**：`hit(key, t)` 按 `hash(key)` 路由到分片子计数器；`getHits(t)` 汇总所有分片。

**面试官最常追问**：
1. **「为什么命中数能直接相加，独立用户数不能？」** → 命中数可加；独立用户数要跨分片
   去重 → 引出可合并的近似去重 sketch（HyperLogLog 的 merge）。
2. **「扩容（分片数变）老数据怎么办？」** → 哈希取模 vs 一致性哈希；后者扩容只搬 1/N。
3. **「各分片时钟不一致，窗口怎么对齐？」** → 逻辑时间 / 由调用方统一传 timestamp 的
   假设边界。
4. **「要一个跨分片全局一致快照怎么办？」** → 协调快照（类似 Chandy-Lamport）vs
   「近似即可就别协调」的取舍。

**取舍表**：

| 维度 | 命中数 | 独立用户数 |
|------|--------|-----------|
| 合并方式 | 直接求和 | HLL merge / 集合并 |
| 内存/分片 | O(窗口) | O(HLL 寄存器数)，固定 |
| 精度 | 精确 | ~1–2% 误差 |

**自检题**：
- 路由保证同一 key 永远落同一分片吗？rehash 时呢？
- getHits 要并行 scatter 吗？某分片慢/挂了，返回部分结果还是报错？
- 「过去 5 分钟独立用户数」要给每个时间桶各放一个 HLL，内存够吗？

### Part 8 — 限流变体（滑动窗口限流器）⭐

**真实场景**：把「数命中」反过来用——API 网关限流。「每用户每 10 秒最多 3 次」，超了
就拒。这是 hit counter 的孪生兄弟，也是面试高频考点。

**问题陈述**：`RateLimiterPart8(W, maxHits)`；`allow(t)` 先看 `(t-W, t]` 内已有多少，
没到上限就接受（计入并返回 `true`），到上限就拒绝（返回 `false` 且**不计入**——被拒
请求不占额度）。

**面试官最常追问**：
1. **「固定窗口计数器有什么毛病？」** → 边界突刺：窗口 `[0,10)` 末尾打 3 次 + `[10,20)`
   开头打 3 次 = 1 秒内 6 次。引出滑动窗口。
2. **「滑动窗口 log vs 滑动窗口 counter？」** → log 存每个请求时间戳（精确，内存随流量
   涨）vs counter 用桶（省内存，边界用加权法估算）。
3. **「和 token bucket / leaky bucket 比？」** → token bucket 允许突发到桶容量、平均
   速率受限；leaky bucket 平滑输出。各自适合什么场景。
   （真实库的 token bucket 长啥样：见 [`Guava-RateLimiter.md`](Guava-RateLimiter.md)。）
4. **「被拒的请求要不要计入额度？」** → 通常不计（否则被拒还占额度，恶意流量能压死
   正常用户）；但要防「狂打被拒」本身的开销。

**取舍表**：

| 算法 | 内存 | 精度 | 突发处理 |
|------|------|------|---------|
| 固定窗口计数 | O(1) | 边界突刺 | 差 |
| 滑动窗口 log | O(窗口内请求数) | 精确 | 好 |
| 滑动窗口 counter | O(窗口/粒度) | 近似 | 较好 |
| token bucket | O(1) | 平均速率 | 允许突发 |

**自检题**：
- 「先判定后记账」和「先记账后判定」结果一样吗？被拒的算不算？
- 边界 `(t-W, t]` 的开闭和「每 W 秒最多 N 次」语义对得上吗？
- 多线程下 allow 的判定+记账不是原子的，会不会放过去 maxHits+1 个？
